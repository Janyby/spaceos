# Архитектура SpaceOS

Срез: 2026-10-18. Документ разделяет подтверждённую концепцию и фактическое устройство; ограничения приведены в [CURRENT_STATE.md](CURRENT_STATE.md).

## Подтверждённые архитектурные решения

1. World — основной экран и главная точка взаимодействия.
2. Shell — дополнительное структурированное представление системы, разделов и инструментов.
3. Интерфейсы используют общую модель Core; отдельное доменное хранилище для каждого представления не требуется.
4. Провайдеры отделяют модель от внешних ресурсов: файловой системы и браузера.
5. Наблюдаемость не заменяет доменное состояние; SpaceTrace не является вторым Core.

Подтверждение концепции World/Shell не означает, что все рабочие сценарии уже доступны непосредственно в World.

## Фактические компоненты и потоки

| Контур | Путь |
|---|---|
| Действие пользователя | World/Shell → HTTP Bridge → Core request_action → Policy → Provider → внешний ресурс |
| Действие внешнего агента | MCP stdio → Bridge → Core request_action → Policy → Provider |
| Наблюдение ресурса | Provider → report_observation → Core → SQLite |
| Переход миссии | HTTP/MCP → валидатор workflow в Bridge → report_observation → Core |
| Внешний MCP-инструмент | HTTP/MCP → зарегистрированный сервер и allow-list в Bridge → MCP client → внешний процесс → запись происхождения результата через Core |
| Чтение | HTTP/MCP → запросы Core и предусмотренные read-only проверки провайдеров |

Последние три контура нельзя безоговорочно описывать как действия через request_action. В частности, внешний MCP-клиент использует собственную проверку разрешений и сохраняет результат через Core.

## World, Shell и окно приложения

Текущий HTTP-маршрут / отдаёт World; Shell доступен через /index.html. World предоставляет обзор и выбор объектов, режимы представления и переходы к действиям. Shell содержит специализированные панели файлов, браузера, миссий, событий и состояния компонентов.

Wry/WebView2 — способ разместить существующий веб-интерфейс в нативном окне. Он не создаёт новую модель данных и не заменяет браузерный провайдер. При самостоятельном запуске runtime может использовать свой встроенный UI вместо Bridge; этот fallback не равен основному World.

## Доменная модель

| Понятие | Представление |
|---|---|
| Object | Идентификатор, тип, свойства, провайдер, внешний идентификатор и временные метки |
| Relation | Типизированная связь между объектами |
| Event | История изменений и действий, корреляция и последовательный курсор seq |
| Space | Запись пространства с идентификатором и метаданными |
| world_id | Идентификатор контекста и фильтр; в объектах находится в свойствах |
| Mission / MissionStep | Типы объектов; шаги соединены связями mission_has_step |
| Action | Запрос внешней операции и связанная цепочка событий |

world_id не является самостоятельной таблицей World и не обеспечивает полноценную границу безопасности между пользователями. Для отношений и событий это отдельное поле; для объектов — свойство.

## Хранилище и наблюдения

Core владеет SQLite. Схема версии 2 включает курсор events.seq, внешние ключи отношений к объектам, индексы и observation_log.

Применение наблюдения атомарно: проверка повторной доставки, запись объектов и связей, подтверждённые удаления, событие и отметка обработки. Повтор observation_id не повторяет применение. Эта гарантия не распространяется на произвольную повторную отправку внешнего действия.

Провайдеры используют report_observation. В Core также сохранены прежние методы записи отдельных объектов, связей и событий для совместимости: нельзя утверждать, что абсолютно все мутации уже проходят через один Observation API.

Транзакция базы не включает файловую операцию или изменение в Chromium. Внешний эффект и его отражение в Core имеют отдельные границы отказа.

WAL доступен через отдельный Storage::open_wal; основной запуск Core вызывает Storage::open и не включает WAL явно. Экспериментальные результаты не доказывают режим конкретной рабочей базы.

## Действия и права

Core проверяет capability до вызова провайдера. История связывает ActionRequested и последующие события через correlation_id действия. Асинхронное сканирование возвращает Started и завершается позднее.

Представляемые клиенту состояния: Queued, Running, Completed, Failed, Denied; Unknown означает отсутствие достаточной истории. Клиентский таймаут не доказывает отмену внешнего эффекта. Отмена миссии не является отменой уже выполненной операции провайдера.

Фактический маршрутизатор выделяет browser, а остальные provider_id направляет в файловый канал. Регистрация нового провайдера сама по себе не создаёт произвольный динамический маршрут.

Файловые операции ограничены разрешёнными корнями. Пустой набор корней по умолчанию запрещает доступ. Запись поддерживает опциональные проверки ожидаемых времени изменения и размера. Локальная гонка между проверкой пути и операцией не устранена полностью.

Согласование миссии проверяется workflow в Bridge. Это не универсальный capability-барьер, запрещающий все альтернативные вызовы действий.

## События, транспорт и восстановление

На Windows IPC использует Named Pipes и JSON-lines. MCP работает по stdio JSON-RPC. Bridge по умолчанию обслуживает loopback HTTP и WebSocket.

События читаются по seq. Подписки Core и HTTP-опрос дополняют друг друга. В WebSocket Bridge реализованы уведомления о состоянии компонентов; полную доставку истории событий через этот канал не следует обещать.

Данные SQLite сохраняются между перезапусками. Агентные токены, подписки и буферы трассировки находятся в памяти. Восстановление требует перерегистрации и перечитывания состояния; незавершённая работа провайдера автоматически не становится возобновляемой.

В коде существуют TCP-ветви для других платформ, но полноценная переносимость этим документом не подтверждается.

## Наблюдаемость

SpaceTrace содержит хуки, буферы, индексы корреляции и диагностические оценки. Буферы локальны процессам. Долговременная межпроцессная история действий находится в событиях Core. Наличие ETW-кода не означает, что сбор включён или разрешён в каждой сессии.
